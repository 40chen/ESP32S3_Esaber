# ESABER ↔ Blender 动捕漂移与延迟 · 根因分析报告

> 分析时间：2026-10-05 ｜ 分析口径：以代码为准（行号引用当前仓库版本）
> 结论适用范围：`shared/review/ESP32S3_Esaber_V2` + 动捕协议 v1（31B/UDP/50Hz）

---

## 0. 一句话结论

**不是"陀螺仪差"一个点的问题**——MPU6050 对 roll/pitch 其实够用。漂移是四层问题叠加：

1. 六轴无磁力计 → **yaw 没有绝对参照，结构性必漂**（物理，无解，只能缓解）
2. **代码里没有陀螺零偏校准**（上电直接用，残偏每秒累积 0.5°~2°，5 分钟漂一圈）
3. **Madgwick 假定固定 100Hz 节拍，但主循环被音频/灯条/Web 挤压** → 节拍抖动直接变成姿态误差，越快挥越歪
4. **位置 = 加速度双重积分，无外部参照** → 必然发散；且姿态漂移会污染重力分离，反过来加速位置跑飞（双重放大）

延迟同源：Madgwick 收敛速度（beta 默认值）+ 主循环串行阻塞造成的帧抖动 + 接收端插值策略未知。

**回答"是否有初始位置校准"：没有。** 全项目 grep 证实不存在任何校准/归零接口——位置无 set/zero API，yaw 无重置通道，唯一"复位"是断电重启（位置清零，但姿态从单位四元数重新收敛，Blender 端模型会跳一下）。

## 1. 根因链（按影响排序）

### R1【物理·结构性】六轴 IMU，yaw 无绝对参照

- `MotionSensor.cpp:84-86`：`filter_.updateIMU(gx,gy,gz,ax,ay,az)` —— 纯 IMU 模式。
- MPU6050 没有磁力计。加速度计只能通过重力矢量校正 **roll/pitch**；**yaw 完全靠陀螺仪积分**，没有任何参照可拉回。
- 后果：yaw 漂移是这条链路的固有属性，Madgwick 算法本身救不了，换 beta、换滤波器都只能缓解。

### R2【代码缺失】陀螺零偏从未校准

- `MotionSensor.cpp:45-55` `begin()`：`initialize()` → 设量程 → `testConnection()`，**没有静止采样求零偏的流程**。
- `update()`（:84-86）直接把原始陀螺读数换算 °/s 喂滤波器，**零偏原样积分**。
- 量化：消费级 MPU6050 上电零偏典型 ±0.5~2°/s，开机自热还会继续漂。**即使只有 0.5°/s 的 z 轴残偏：30 秒漂 15°，5 分钟漂 150°**。这解释了"越用越歪"。
- 对比：这是全链路里**性价比最高的修复点**（约 15 行代码），却缺失了。

### R3【代码缺陷】Madgwick 固定采样率假设 vs 主循环节拍抖动

- `MotionSensor.cpp:20`：`kFilterRateHz = 1000/MotionInterval = 100Hz`，`begin(100)` 后，**无 dt 的 `updateIMU()` 走内部固定 invSampleFreq**。但注意（通用助手复核修正）：lib_deps 锁的 `Madgwick@^1.2.0` 恰好已提供带 `deltat` 的重载 `updateIMU(gx,gy,gz,ax,ay,az,deltat)`，可直接喂实际 dt——代码里算好的 `deltaTime`（:61）目前只喂了位置积分，姿态融合没吃到。P0-3 独立任务锁节拍仍是更彻底的架构解，两者可并用。
- 实际节拍：`SystemController::update()`（:114-124）单任务串行——**音频泵优先**（`SaberController.cpp:85-86` `audio_->loop()` 每圈必须喂，SD 卡读 + 解码阻塞）→ Web 请求 → settings → **遥测** → 按钮。挥剑瞬间恰好是音频/灯效负载最重的时刻。
- 主循环某圈被拖到 30-50ms 时，Madgwick 仍按 10ms 积分 → **该圈角位移被低估 50-80%**。
- 后果：**越用力挥，姿态越跟不上、越歪**——和实际体验高度吻合。同时遥测名义 50Hz 实际掉帧，Blender 端观感即"延迟 + 卡顿"。
- 附注：代码里算了 `deltaTime`（:61）但只喂给位置积分，姿态融合没享受这个正确性。

### R4【结构性】位置双重积分必发散，且被姿态漂移二次污染

- `MotionSensor.cpp:111-127` `updatePosition()`：体轴加速度旋转到世界系 → 减重力 → 死区 0.15 m/s² 清零 → 速度/位置双重积分 → ±2m 钳位。
- 三层问题：
  1. **双重积分对任何残差都是平方级放大**（0.05 m/s² 残差 → 10 秒积出 2.5m）；死区只能止损，不能纠偏——位置漂了就是漂了。
  2. **姿态污染位置**：`rotateToWorld()` 用当前四元数分离重力（:113）。R1/R2/R3 导致的 yaw 漂移会让旋转矩阵跟着歪，重力分量泄漏进水平轴——这种泄漏是慢变信号，**很容易超过 0.15 m/s² 死区**，死区拦不住，位置开始匀速跑。漂移越久，位置跑得越快。
  3. 死区 0.15 m/s² ≈ 1.5%g，**小于这个程度的真实运动全部被吞掉**——小步移动在 Blender 里根本不动，大残差又拦不住，两头不讨好。
- 结论：没有外部参照（光学/Vive tracker/UWB）的航位推算位置，**在消费级 IMU 上只能当玩具**。这是方案级结论，不是实现 bug。

### R5【配置】陀螺量程 ±250dps 对"光剑"场景严重不够

- `HardwareConfig.h:120` `GyroLsbPerDegree = 131`（±250°/s 满量程），`MotionSensor.cpp:48` 对应设置。
- 成年人手腕快挥 500~1500°/s 是常态——**超量程 2~6 倍，输出削顶**，Madgwick 在快挥时拿到的是被砍头的角速度。
- 后果：快挥瞬间姿态丢失/回弹；同时挥动判定阈值（`SwingThreshold` 等基于原始 LSB，:127-133）在饱和区失去区分度。

### R6【配置】Madgwick beta 未调

- 库默认 beta=0.1，项目未覆盖。beta 小 = 平滑但**跟随慢（百毫秒级滞后）**；快动作时模型"拖影"。
- 这直接贡献"延迟高"的主观感受。

### R7【次要】欧拉角往返重建四元数

- `MotionSensor.cpp:89-103`：滤波器内部本来就是四元数，这里却 `getRoll/Pitch/YawRadians()` 再用欧拉角重建四元数发出去。
- 代价：pitch ≈ ±90°（竖劈）附近欧拉角退化（万向锁），重建四元数会抖；且多一道数值折返。
- Madgwick@1.2.0 有 `getQuaternion()` 可直取，应当砍掉往返。

## 2. 延迟专项拆解

| 嫌疑点 | 结论 |
|---|---|
| Madgwick beta 默认值 | **实锤**。跟随滞后百 ms 级（R6） |
| 主循环串行阻塞（音频/灯条/Web） | **实锤**。帧间隔抖动 + 姿态误差（R3），遥测实际帧率 < 50Hz |
| UDP 链路本身 | 排除。31B 小包、无重传堆积、发的是最新快照 |
| beacon 拉长（改动③） | **排除**。`WifiService.cpp:35` 注释证实 API 在当前 IDF 不可用，beacon 仍默认 100ms |
| 接收端积压（通用助手补充嫌疑，延迟递增型） | **高度可疑，待指纹验证**。固件 50Hz 发、Blender ~24fps 渲染消费，若脚本每帧只 recv 一包且不清缓冲，UDP 队列每秒净积压 26 帧 → 延迟随使用时间线性增长（缓冲耗尽后稳定在高位）。**验证指纹：刚连设备时跟手、越用越拖 = 铁证**；刚连就延迟则指向固件节拍/无线链路。修复：recv 循环读空内核缓冲、只留最新一帧渲染（经典动捕接收端模式）。`blender_receiver.py` 不在仓库内，需管理员提供实物脚本核对 |
| 接收端（Blender 脚本） | **无法审计**——`esaber-blender-link/PROTOCOL.md` 与接收端脚本不在当前交付包内（`tools/` 为空）。若脚本按收帧直接 set 姿态、无 SLERP/低通，观感延迟会再放大一档 |

## 2.5 症状 → 根因指纹对照（先定位症状再对症下药）

| 你看到的现象 | 主嫌根因 | 对应修复项 |
|---|---|---|
| 静止/慢用时模型慢慢转歪、越用越歪 | R2 零偏未校准 + R1 无磁力计（时间累积型） | P0-1、P2-9 |
| 快挥时模型跟不上、甩过头再弹回 | R5 ±250dps 饱和 + R3 时基错配（瞬时型） | P0-3、P0-4 |
| 模型平移自己乱跑/漂出场地 | R4 双重积分无参照（+姿态漂移二次污染） | P0-2、P2-11 |
| 延迟刚连还行、越用越大 | 接收端 UDP 积压（递增型延迟） | P1-7 |
| 延迟恒定偏高、动作拖影 | R6 beta 收敛慢 + R3 主循环挤占 + 无插值 | P0-3、P0-6、P1-7 |
| 竖劈/垂直挥动时姿态跳变 | R7 欧拉往返万向锁 | P0-5 |

## 3. 修复路线图

### P0 · 纯软件速效（预计显著改善，小时级工作量）

1. **上电零偏校准**（R2，收益最大）：开机要求静止 1~2 秒，采 100~200 组陀螺读数取均值作为 bias，`update()` 中逐次扣除；顺手在 Web 控制台加"重新校准"按钮。
2. **加归零 API**（R4 + 回答用户）：位置/速度清零 + yaw 重置（把当前 yaw 作为一个参照并归零输出）。Web 端点或协议加 1B 命令均可。给 Blender 演示一个"随时正姿"的锚点。
3. **IMU 搬独立任务**（R3，架构正解）：ESP32-S3 双核，pin IMU 采样+融合到 core 1 用 `vTaskDelayUntil` 锁 100Hz，主循环只取最新快照。节拍抖动、遥测掉帧、快挥削误差三个问题一次解决。
4. **陀螺量程 ±250 → ±2000dps**（R5）：`GyroLsbPerDegree` 131→16.4，两处常量联动。选 ±2000 而非 ±1000（通用助手复核修正）：R5 自引的快挥峰值 500~1500°/s 已顶穿 ±1000 量程，急停/碰撞弹开会再次削顶，±2000 一次到位。**注意**挥动/碰撞阈值基于原始 LSB 会缩水 8 倍（131→16.4），需重新标定（建议阈值判定也改用物理单位 °/s，一劳永逸）。
5. **直取四元数**（R7）：`filter_.getQuaternion(w,x,y,z)` 替换欧拉角往返。
6. **beta 调参**（R6）：0.1 → 0.3~0.5 实测，跟随速度与噪声取平衡。

### P1 · 接收端与协议（需要 Blender 端脚本进包）

7. Blender 侧按 60fps 渲染，对 50Hz 四元数做 **SLERP 插值**、位置做低通/指数平滑——观感延迟可再降一档。
8. 协议 v1 → v1.1：帧里加"校准状态/归零事件"标志位。

### P2 · 硬件路线（根治 yaw 与位置）

9. **加磁力计**：QMC5883L（数元级成本，I2C 同总线挂 GPIO1/2）→ Madgwick 换 9 轴 `update()`，yaw 获得绝对参照，漂移根除。
10. 或一步到位 **BNO085**（出厂融合芯片，I2C 直接吐校准好的四元数，游戏动捕常用）——替换 MPU6050 + Madgwick 整条链。
11. **位置动捕换外部参照**（Vive tracker / 光学），或干脆在协议层接受"姿态-only"：光剑场景里姿态 + 音效已经承载绝大部分沉浸感，航位推算位置建议标记为演示特性、默认关闭。

## 4. 验证方法（改完怎么证明有效）

1. **零偏校准验证**：设备静止平放，Web 控制台看 yaw 读数 5 分钟——校准前漂 X°/min，校准后应较校准前**降低一个量级、典型 < 1~2°/min**。注意（通用助手复核修正）：0.1°/min 是现代 IMU/BNO085 的验收口径，MPU6050 受残余温漂所限达不到——若按此验收，会把有效修复误判为失败。
2. **节拍抖动验证**：串口打印 `update()` 实际间隔直方图；IMU 独立任务后应稳定 10±1ms。
3. **饱和验证**：慢挥 vs 快挥对比四元数角变化量，±2000dps 后快挥不再"砍头"。
4. **端到端延迟**：Blender 端记录帧序号 + 本地时间戳，统计 P50/P95 帧间隔；插值前后对比录屏逐帧数。
5. **回归**：挥/砍/旋腕阈值重新标定后跑一遍功能说明书"七种灯效/动作阈值"清单。
