## 一、结论速览

**"陀螺仪差"只占漂移成因的三分之一。** 真实构成是：

| # | 因素 | 归属 | 对漂移的贡献 | 修复成本 |
|---|------|------|------------|---------|
| ① | 陀螺量程 ±250°/s **饱和** | 配置错误 | 挥动后大偏差的**主凶** | 一行 |
| ② | 陀螺零偏**从未校准** + 无磁力计 | 算法缺失 + 硬件天花板 | 静止时 yaw 缓慢漂移 | 十几行 / 换件根治 |
| ③ | 位置航位推算**双积分无回中** | 算法结构性缺陷 | 模型位置乱飞/卡边的**主凶** | 小时级 |
| ④ | Madgwick 用名义采样率，实际 dt 没喂进去 | 算法缺陷 | 姿态抖动、精度损失 | 几行 |
| ⑤ | 欧拉角→四元数往返重建（舍近求远） | 冗余实现 | 万向锁附近姿态跳变 | 一行 |
| ⑥ | UDP 接收端脚本**在仓库中不存在**，无法审计 | 工程缺失 | 未知盲区 | 需要您提供 |

**回答您的核心问题**：MPU6050 确实是 2011 年代的消费级 6 轴，零偏温漂显著、无磁力计——它是"天花板"较低；但把天花板压到地上的是 **①量程饱和** 和 **③位置双积分** 这两个配置/算法问题。不修这两项，换再好的 IMU 也一样漂。

## 二、数据链路现状（代码实证）

```
MPU6050 (I2C, 100Hz, MotionInterval=10ms)
  → MotionSensor::update()
      → getMotion6() 原始六轴
      → Madgwick.updateIMU()        ← 用名义 100Hz 积分（④）
      → getRoll/Pitch/YawRadians()
      → 手工重建四元数               ← 舍近求远（⑤）
      → updatePosition() 航位推算    ← 双积分+死区+钳位（③）
  → MotionTelemetry::update()（50Hz, UDP 31B 定长帧 → 192.168.4.2:5005）
  → Blender（接收端脚本缺失 ← ⑥）
```

关键配置（`include/HardwareConfig.h` L116-122）：

```cpp
constexpr uint16_t MotionInterval = 10;        // 100Hz 采样
constexpr uint16_t TelemetryInterval = 20;     // 50Hz 发送
constexpr float AccelLsbPerGravity = 2048.0f;  // ±16g 量程
constexpr float GyroLsbPerDegree = 131.0f;     // ±250dps 量程  ← 问题①
constexpr float PositionDeadZone = 0.15f;      // ≈15mg，挡不住零偏
constexpr float PositionLimit = 2.0f;          // ±2m 钳位
```

## 三、逐项分析

### ① 陀螺量程 ±250°/s 饱和 —— 挥动后大漂移的主凶

`MotionSensor.cpp` L48：

```cpp
imu_.setFullScaleGyroRange(MPU6050_GYRO_FS_250);   // ±250°/s：挥动精度
```

注释里"挥动精度"这个判断是反的。**真实挥剑动作的角速度在 500~2000°/s 量级**（手腕急停、碰撞弹开更高），±250°/s 量程下这些动作全部被钳位在 32767（即恒定 250°/s 输出）。

后果链条：

1. 挥动期间陀螺输出远小于真实角速度 → Madgwick 积分的转角严重不足 → 模型"跟不上"
2. 停止挥动后，roll/pitch 有重力锚定，Madgwick 的加速度计修正项会慢慢拉回来；
3. **yaw 没有锚定**（无磁力计），欠积分的 yaw 误差永远留在姿态里 → 挥几次后模型朝向与现实严重不符。

**漂移指纹**：挥动越猛、越频繁，模型朝向偏得越厉害；静置时反而不怎么漂。

**对策（一行）**：

```cpp
imu_.setFullScaleGyroRange(MPU6050_GYRO_FS_2000);   // ±2000°/s：16.4 LSB/(°/s)
```

同步把 `HardwareConfig::GyroLsbPerDegree` 从 131.0 改为 **16.4**。±2000°/s 档位灵敏度 0.06°/s/LSB，100Hz 采样下对慢速动作的分辨能力完全够用（慢动作时 Madgwick 靠加速度计主导修正），而快速挥动不再饱和。

### ② 陀螺零偏从未校准 + 无磁力计 —— 静止 yaw 漂移，硬件天花板

两个独立子问题：

**a) 零偏校准缺失**。`MotionSensor::begin()` 只做了 initialize + 量程设置 + testConnection，**没有任何开机零偏采样**。MPU6050 个体零偏普遍在每秒零点几度到几度量级（视个体与温度），直接进积分就是持续转圈。消费级 IMU 的标准做法是开机静置采几百个样本取均值当零偏，运行时减掉——十几行代码。

**漂移指纹**：光剑静置桌上不动，Blender 模型仍在缓慢自转（通常是绕竖直轴）。

**b) 无磁力计的结构性限制**。MPU6050 是 6 轴（无地磁参考），Madgwick `updateIMU` 模式下 yaw 纯靠积分，**任何 yaw 误差都是永久性的**，加速度计只能修 roll/pitch。零偏校准能把静置漂移压低一个量级，但温漂仍在——这是 6 轴方案的物理天花板。

**对策分三级**：
- 短期（十几行）：上电零偏校准——`begin()` 里静置采 500 样本求均值，`update()` 里减去；
- 中期（免费）：接受 yaw 漂移，在 Blender 端加一个"回正"快捷键演示时手动归零；
- 根治（硬件）：换 9 轴 IMU（如 ICM-20948/LSM9DS1，或直接 ICM-42688 这类现代 6 轴，零偏稳定性好一个量级以上）。

### ③ 位置航位推算双积分无回中 —— 模型位置乱飞的主凶

`MotionSensor.cpp` L111-127。这个通道有三个叠加的结构性问题：

**a) 死区挡不住零偏**。`PositionDeadZone = 0.15 m/s² ≈ 15mg`，而 MPU6050 加速度计的初始零偏容差在几十 mg 量级（±16g 量程下 1 LSB 就是 0.49mg，零偏几十上百个 LSB 很正常）。**零偏大于死区的个体，世界系下减重力永远减不干净**，残余恒定加速度每轴零点零几到零点几 m/s²，速度线性增长、位置二次增长，一路漂到 ±2m 钳位卡住。注释里说"旧的除数 bug 让位置饱和在钳位上"——除数修好了，但**零偏大的个体依然会饱和，只是慢一点**。

**b) 速度回零、位置不回零**。死区内 `velocity_` 清零但 `position_` 保留——位置没有回中机制。挥剑中飞出去的位移永远停在原地，用一段时间后模型就"挂"在某个随机偏移处。

**c) 挥剑必然触发积分**。0.15 m/s² 的死区远小于挥剑加速度（几 m/s² 到几十 m/s²），每次挥动速度都大积分，急停靠死区清零速度，但位移已经发生。

**漂移指纹**：模型位置越用越偏，或者干脆卡在原点周围 ±2m 的某个边缘不动了。

**对策分两级**：
- 快速止血：**Blender 端停用位置跟随，只用姿态**。姿态 + 模型位置锚定在手中，观感已经足够"动捕"；位置通道是单 IMU 做不到位的伪需求；
- 若坚持要位置：死区提到 0.3~0.5 m/s²，加"静止 2 秒后位置按指数衰减回中"，并接受它是低精度暗示性跟随。

**管理员的预期管理**：单 6 轴 IMU 的航位推算，在学术上就是几秒内发散的东西，消费级 VR 手柄都要靠外部定位（摄像头/基站）才能做位置。这不是代码写错，是物理。

### ④ Madgwick 时基错配 —— 抖动与精度损失

`filter_.begin(kFilterRateHz)` 把名义 100Hz 烧进滤波器；`updateIMU()` 内部按这个名义频率积分。实际节拍靠主循环轮询，音频解码最优先（`SystemController.h` L20-21 注释自述"音频解码最优先"），SD 卡读、灯条 show()、WiFi 事件都会让 `MotionSensor::update()` 的实际间隔抖动。`deltaTime` 算出来了，**但只喂给了航位推算，Madgwick 没吃到实际 dt**。

**对策（几行）**：MadgwickAHRS 新版支持带 dt 的重载 `updateIMU(gx, gy, gz, ax, ay, az, deltaTime)`，把已有的 `deltaTime` 传进去即可；滤波器 `begin()` 的频率参数就只影响初始 beta。

### ⑤ 欧拉角→四元数往返重建 —— 万向锁附近的跳变源

`MotionSensor.cpp` L88-103：从 Madgwick 提取 roll/pitch/yaw 欧拉角，再手工用三角函数重建四元数。Madgwick 库有 `getQuaternionW/X/Y/Z()` 直接输出内部四元数——绕行欧拉角没有收益，只有成本：

- 非奇异区域数学上等价，但引入浮点往返误差（次要）；
- **pitch → ±90°（刀尖垂直朝天/朝地）时欧拉角奇异**，getRoll/getYaw 的分离结果跳变，重建四元数跟着跳——模型在该姿势附近会抽动。

**对策（一行）**：删掉 L89-103 的提取+重建，直接 `filter_.getQuaternionW()` 等四个值填 `data_.quaternion`。

### ⑥ 接收端契约缺失 —— 审计盲区 + 工程隐患

README L23 与 `MotionTelemetry.cpp` L3 都声称契约在 `shared/esaber-blender-link/PROTOCOL.md` + `blender_receiver.py`，**但这两个文件在整个 shared 目录树中不存在**（已 Glob 全量核实）。意味着：

- Blender 端如何解释四元数（轴向映射、wxyz/xyzw 顺序、Blender 的 -Z 朝上约定）、是否检查序号丢包、是否插值，全部无法审计；
- 协议"唯一真相源"丢失，固件端按 v1 发，接收端若还是旧 CSV 逻辑或另一版本，两边各说各话——**这本身就能产生"模型间漂移"观感**（坐标系映射错了表现为恒定偏转/镜像，不是缓漂，可据此区分）。

## 四、延迟高的嫌疑链（管理员补充症状，2026-10-05 22:45）

延迟与漂移是两条独立诊断线。按数据流向排查：

| 环节 | 机制 | 延迟量级 | 指纹 |
|------|------|---------|------|
| A. 固件主循环阻塞 | 音频解码最优先、68 颗灯条全帧重算 + show()、CPU 已为供电优化降到 160MHz → motion/telemetry 排队等节拍 | 几十 ms 抖动，**不累积** | 模型偶尔顿一下 |
| B. **Blender 端消费速率 < 生产速率** | 固件 50Hz 发送，Blender 约 24fps 渲染消费。若接收端**每帧只读一个包且不清空 socket 缓冲**，UDP 接收队列净积压：每秒积 26 帧，**一分钟积压 1560 帧 ≈ 31 秒延迟** | 秒级起步，**越用越大** | **刚连上很跟手，用几分钟后越拖越远** |
| C. AP 无线链路 | beacon 已拉长到 300ms（供电优化③）、客户端省电模式、2.4G 干扰重传 | 几十~几百 ms 抖动 | 无规律卡顿、偶发丢帧 |

**B 是"延迟也很高"的第一嫌疑**，且与"漂移严重"并发完全自洽——积压既造成延迟，积压期间的旧姿态数据套上去也表现为"模型跟不上"。固件端 TelemetryInterval 20ms 无需改小（改小反而加重积压），**关键在接收端必须"每次读空缓冲、丢弃旧包只留最新一帧"**。

**30 秒验证法**：Blender 刚连上设备时延迟如何？
- 刚连跟手、越用越拖 → 铁证是 B，改接收端消费策略即可根治；
- 刚连就延迟 → A/C（固件节拍或无线链路），再按指纹细分。

## 五、修复优先级路线

**第一档 · 半小时级（固件三小改，预计立竿见影）**
1. 陀螺量程 250→2000：`MotionSensor.cpp` L48 + `HardwareConfig.h` L120（GyroLsbPerDegree 131→16.4）
2. 开机零偏校准：`MotionSensor::begin()` 静置采 500 样本均值，`update()` 减去
3. Madgwick 传实际 dt：改用带 deltaTime 的 updateIMU 重载

**第二档 · 小时级（结构性止血）**
4. 四元数直取替代欧拉重建（⑤）
5. Blender 端停用位置跟随，只跟姿态（③快速止血）；或死区上调+静止回中
5b. **接收端"丢旧保新"**：每次渲染帧读空 UDP 缓冲只留最新包（⑦根治延迟累积）
6. 验收标准建议：静置 1 分钟 yaw 漂移 < 2°；标准挥剑 10 次后朝向偏差 < 15°；连续使用 5 分钟延迟无可感增长

**第三档 · 根治（可选硬件）**
7. 换 9 轴或现代 6 轴 IMU（零偏稳定性、量程、DMP 都是代差提升）
8. 真位置追踪需外部定位，单 IMU 无解——建议放弃位置通道

**顺手整改**
9. 补齐 `PROTOCOL.md` + `blender_receiver.py` 入仓（README 已承诺但缺失），否则 #6 的两端核对无法闭环
